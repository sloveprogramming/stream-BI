> 日期：2026-10-10
> 状态：**待评审**（未动任何代码）
> 调整动因：用户是 AI 应用开发工程师，要求技术栈对齐**市场招聘 AI 应用开发工程师**的主流要求
> 与 v1 的关系：**v1（`2026-10-10-BIsql数据中台改造方案.md`）的需求梳理与角色/落地路线继续有效**；本稿**替换 v1 第 4/5/6 章的技术选型**，并把「AI 能力」从"出口之一"提升为**贯穿全链路的主线**

---

## 0. 三条调整原则

1. **AI 应用为主线，数据工程为底盘。** 招聘方看的是「你会不会做 AI 应用」，不是「你会不会做 ETL」。所以数据编排不能是纯 ETL —— **算子库里必须有 AI 算子，平台每个环节都要有 AI 落点**（见第 4 章）。
2. **每层都用 2026 的事实标准，不自研。** 自研方案在面试里讲不出分量（"你为什么不用 dbt"是个必被问的问题）。能白拿的能力（dbt 的血缘/测试/文档、Dagster 的资产图、GE 的报告）一律不自己写。
3. **不加运行时负担。** 单机、单人维护、百人规模 —— 只有能**同时**服务"招聘要求 + 真实可用"的组件才引入；Spark/Flink/K8s/Airflow/OpenMetadata 一律不进。

## 2. 关键选型决策（证明"主流"）

### 2.1 数据转换：自研 DAG→CTE 编译器 → **dbt Core**

| 候选 | 结论 |
|---|---|
| **dbt Core** | ✅ **选它**。2026 转换层事实标准（"dbt won the transformation layer"）。**白拿**：DAG 依赖、血缘、测试（not_null/unique/accepted_values/relationships）、文档站点、版本化 SQL |
| SQLMesh | 现代化挑战者，DX 更好，但生态小、社区资料少 |
| 自研编译 | v1 方案。**面试会被问"为什么不用 dbt"**，且要自己写测试/文档/血缘 |

**落地方式**：拖拽画布 **不是**取代 dbt，而是 **dbt 的可视化前端** —— 画布上的算子编译成 dbt model + `schema.yml`（含 tests + 中文 description），`dbt build` 执行。**画布做易用性，dbt 做工程严谨性**，两者不冲突，这是最容易被面试官认可的设计。

### 2.2 执行引擎：**DuckDB + PG 下推**（不上 Spark）

- **DuckDB**：2026 本地 OLAP 标准（"用 DuckDB 做所有事，直到你不得不换"）。进程内、零部署、可直接读 PG 与 Parquet、列式极快；
- **PG 下推**：简单算子/大表直接在 PG 里算，数据不出库；
- **Polars**：DuckDB 表达不了的复杂算子兜底；
- **不上 Spark/Flink**：单机、单人、数据量中小。引入即灾难。

### 2.3 调度：APScheduler → **Dagster**

| 候选 | 运维footprint | 结论 |
|---|---|---|
| **Dagster** | webserver + daemon + PG = **3 个进程** | ✅ **选它** |
| Prefect 3 | server + workers（自托管更重） | 备选（更轻的 Python 心智，但无原生血缘） |
| Airflow | scheduler+webserver+DB+Redis+N workers = **5–6 个** | ❌ 单人维护太重 |
| APScheduler（v1） | 0 | 保留跑旧同步任务 |

**为什么是 Dagster**（引用 2026 选型共识）：
> "Is your pipeline mostly **dbt plus warehouse tables**? **Dagster**, whose model maps almost exactly onto that shape."

我们的形态正好是「接入 → dbt → 数据集/BI」，且**Dagster 的软件定义资产（Software-Defined Assets）模型 = 我们"编排产物即数据集"的概念**。白拿：
- **原生血缘**与**跨管线资产图**（省掉自研血缘）；
- **新鲜度（freshness）与分区**（直接回答监控看板的"哪些表过期了、为什么"）；
- **dbt 集成一等公民**：每个 dbt model 自动变成一个 Dagster asset；
- 类型安全 + 一等测试能力 + 最好的本地开发体验（`dagster dev` 秒起 UI）。

**迁移策略（只加不换）**：APScheduler **保留**跑现有 `sync_*`/`monitor_*` 任务；**新编排一律走 Dagster**，稳定后把同步任务逐步迁为 Dagster asset。

### 2.4 数据质量：自研质量算子 → **dbt tests + Great Expectations**

- **dbt tests**：模型层（主键唯一、非空、值域、外键关系）—— 已在 dbt 里，零额外成本；
- **Great Expectations**：表级**六维度**校验（完整性/唯一性/有效性/准确性/一致性/及时性）+ **自带 Data Docs 报告站点** → **直接当质量看板用，不用自己画**；
- 备选更轻的 **Soda Core**（YAML 声明式）。

### 2.5 向量库：**pgvector**（不是 Milvus）

| 候选 | 结论 |
|---|---|
| **pgvector** | ✅ **选它**。零新增服务；与业务数据**同库同事务**（向量列可以和业务表在一起，能直接 JOIN 过滤权限）；JD 明确列了 pgvector；语料规模（几千~几十万条）完全够 |
| Milvus | 你智聘云已用 → **这是加分谈资**，但本项目单机会多一个重服务（需 etcd + MinIO + 多组件） |
| Qdrant / Weaviate | 单容器可接受，但仍多一个服务；规模化后的替换路径 |

**面试话术**：*"我用过 Milvus，但这个项目选 pgvector —— 因为数据规模小、要跟业务表做行级权限 JOIN、且单人维护不想多一个中间件。检索接缝是抽象的，规模上去可换 Qdrant。"* —— 能讲清**为什么**才是招聘方要的（JD 原话："知道向量库的名字说明不了什么，重要的是能不能解释检索为什么召回错了、你会改什么"）。

### 2.6 语义层：自研 Ossie 风格 YAML → **dbt MetricFlow**

- **dbt MetricFlow**（dbt Semantic Layer 开源部分）：指标定义（`name / synonyms / formula / grain / dimensions`）版本化在 dbt 项目里，与模型同源；
- 编排里的"派生字段"**引用指标口径**，口径改一处、全链路跟着变；
- 出口仍走**自研 MCP Server**（已有），把指标暴露给 Agent —— 这就是 2026 主流的 **"MCP 管通道、语义层管含义"**。

### 2.7 血缘与可观测

- **数据侧血缘**：`OpenLineage` 事件格式（2026 新兴标准）+ Dagster 资产图可视化。**不自研血缘存储**；
- **LLM 侧追踪**：**Langfuse**（每次 Agent 运行留 trace：prompt/SQL/tool calls/token 成本/耗时）；不想引 ClickHouse 就用 **Arize Phoenix**（单容器、OTel 原生、轻量）；
- **指标监控**（Prometheus + Grafana）：**先不引**，Dagster UI + Langfuse 已覆盖大半。

### 2.8 评测：自建 → **RAGAS + DeepEval + 自建**

| 评什么 | 工具 |
|---|---|
| 检索质量（召回/重排） | **RAGAS**（context precision/recall、faithfulness） |
| Agent / LLM 输出质量 | **DeepEval**（含 LLM-as-Judge、幻觉、相关性） |
| Text-to-SQL 准确率 | **自建 execution accuracy**（v1 已规划，行序无关比对） |
| 评测集 | 50–100 条真实业务问题 + **人工核对**的期望结果（禁止模型生成） |

**这一块是面试的硬通货**：JD 明确写 "Build comprehensive evaluation frameworks"。你 v1 简历里那个 `【待填】问数准确率`，靠这套能填上。

### 2.9 前端：**React 18 + TypeScript + React Flow**

- **React Flow（@xyflow/react）**：Dify / Flowise / LangGraph Studio 都用它，是编排画布的**事实标准**；你的前端已是 React + Ant Design，零迁移成本；
- 备选 AntV X6（内置对齐线/撤销重做更全，但学习曲线陡、体积 ~180KB vs ~95KB）；
- 状态管理 **Zustand**（React Flow 官方推荐搭配）+ **TanStack Query**（服务端状态）+ **ECharts**（看板图表）；
- **TypeScript 是 AI 应用前端的标配**（JD 常见 "Node.js / TypeScript" 加分项）。

### 2.10 数据接入：保留自研 + **dlt** 接新源

- 自研 ERP 同步引擎**已跑通**（整库扫描 + 水位线 + 结构自动演进），保留；
- **非 ERP 新源**（竞品库 / BOM / 物流账单 / HR / 生意参谋）用 **dlt**（data load tool）：纯 Python、约 10 行接入、自带 schema evolution 与增量、无基建 —— 2026 轻量接入主流（"忘掉 Airbyte 的复杂度和 Fivetran 的价格"）。

## 4. ⭐ AI × 数据中台：六个融合点（本方案的核心亮点）

**这是把"AI 应用开发"和"数据中台"焊在一起的地方。** 每个点都对应 JD 里的硬指标，且都是**真实业务需求**，不是硬凑。

### 4.1 AI 算子进算子库（最重要）

算子库除传统 ETL 算子外，新增 **AI 算子** —— 画布上可以和「过滤」「JOIN」直接连线：

| AI 算子 | 干什么 | 真实业务场景 |
|---|---|---|
| `llm.classify` | 文本分类打标 | **商品标题 → 类目自动映射**（直接解决 09-21 记的"类目映射是运营最大障碍"） |
| `llm.extract` | 非结构化 → 结构化字段抽取 | 客服聊天记录 → 问题类型/紧急度 |
| `llm.judge` | 智能判定 | 判断订单是否异常、评论是否差评 |
| `embed.text` | 文本向量化 → 写入 pgvector 列 | 商品描述向量化，供语义检索 |
| `dedup.semantic` | **语义去重**（向量相似度） | 「新农哥碧根果」vs「新农哥碧根果（袋装）」判为同一商品 —— 精确去重做不到 |
| `retrieve.vector` | 向量检索召回 | RAG 召回、相似商品推荐 |
| `llm.rule_suggest` | 生成候选质量规则 | 见 4.4 |

**技术要点**：LangChain + **Pydantic structured output**（保证输出可解析）+ 批量并发 + **token 成本与限流控制** + 结果缓存（同输入不重复调 LLM）。
**为什么这是亮点**：传统 ETL 平台处理不了「非结构化文本」和「语义判断」，而这两类正是 AI 的强项。**这是数据中台与 AI 应用的真正结合点，不是套壳。**

### 4.2 NL → Pipeline：自然语言生成数据管道

用户说「我要一张每天各仓的库存周转表」→ **LangGraph Agent** 规划 → LLM 结构化输出 **DAG JSON** → 渲染到 React Flow 画布 → **人工确认后运行**。

- 算子库的每个算子 = 一个 **tool schema**（JSON Schema），Agent 按 schema 生成合法 DAG；
- 用 **LangGraph `interrupt`** 做人工确认闸门（契合"预览后再执行"）；
- 生成的管道是**可读的 dbt SQL**，不是黑盒。

**技术关键词**：Agentic Workflow / Tool Calling / Structured Output / HITL —— 全是 JD 高频词。

### 4.3 NL → SQL 问数 Agent（已有，用 v2 技术栈强化）

LangGraph `plan → act → reflect → clarify → answer`（已实现）+ **v2 增量**：
- **混合检索 Schema**：表多时先检索相关表（BM25 + 向量 + RRF + bge-reranker），不再全量塞 prompt；
- **动态 few-shot**：检索已验证的 Q-SQL 对注入（已有 bigram 版 → 升级为 **pgvector + BGE-M3**）；
- **语义层对齐**：问"销售额"先对齐 MetricFlow 里的口径，不再猜支付口径还是回款口径；
- **反思重试**（已有）+ **RAGAS/DeepEval 量化**。

### 4.4 AI 质量规则推荐
扫描数据画像（null 率、基数、值分布、样本值）→ LLM 生成候选六维度质量规则（含 YAML/GE 表达式）→ 人工确认后写入。**对标 Dataphin 的「X-数据质量」**，把"治理"这件苦活交给模型起稿。

### 4.5 AI 异常归因（已有 monitor 模块）
统计基线（环比/同比/3σ）触发 → 复用 4.3 的 Agent 循环多步下钻（维→渠道→SKU）→ 生成简报（含 SQL 依据 + 建议动作）→ 推钉钉 + `interrupt` 确认后建待办。**成本模型**：轮询用规则（便宜）、归因才用 LLM（贵）。

### 4.6 AI 元数据与资产打标
LLM 为表/字段自动生成**中文名、业务描述、业务域标签、敏感级别**（对标 Dataphin「X-数据管家」）。这一步让"**数据找人**"成立 —— 也是资产看板与权限分级的输入。

**这六点合起来，把 LangGraph / RAG / 混合检索 / 向量库 / Embedding / Rerank / Structured Output / Tool Calling / MCP / Prompt & Context Engineering / Memory / 评测 / 可观测 全部用上，而且每一处都有业务理由。**

## 6. 落地路线（v2）

v1 的 S1–S6 更细，这里给 v2 覆盖后的版本（**仍建议先做 S1+S2**）：

| 阶段 | 内容 | 关键验收 |
|---|---|---|
| **S0 环境对齐** | Docker Compose 加 `postgres+pgvector` / `redis` / `dagster`；dbt 项目骨架（`dbt_project.yml`）；Langfuse 或 Phoenix 接入；RAGAS/DeepEval 装好 | `dbt build` 跑通空项目；Langfuse 里能看到一条 trace；评测脚本能输出一个数字 |
| **S1 编排地基** | 算子库（12 MVP 传统算子 + **6 个 AI 算子**）；画布 DSL → **dbt model + schema.yml 编译**；Dagster 资产化；`/api/v1/flows` | 不写代码能拼「读→去重→过滤→AI 打标→物化」并跑出 dbt model；Dagster UI 看到资产与血缘 |
| **S2 画布** | React 18 + TS + React Flow；算子面板；JSON Schema 自动表单；连线校验；**每步预览**；运行日志流 | 拖拽出一条管道并跑通；产物自动注册为数据集、权限生效 |
| **S3 治理** | dbt MetricFlow 指标；GE 六维度规则 + Data Docs；OpenLineage 血缘；AI 元数据打标（4.6）+ AI 规则推荐（4.4） | 口径统一；质量看板有分；血缘可追到 ERP 源字段 |

| **S5 看板** | Dagster/质量/资产 三张内部看板 + **4 个角色业务看板** | 业务人员自助可见；行级权限在业务看板生效 |
| **S6 NL→Pipeline** | LangGraph 生成 DAG + interrupt 确认 | 一句话生成可运行管道，人工确认后执行 |
| **S7 多源** | dlt 接入 1 个非 ERP 源 | 跨源编排跑通 |

## 9. 风险与成本

| 风险 | 说明 | 应对 |
|---|---|---|
| **组件变多，单人维护压力上升** | 从 ~4 个容器到 6–8 个 | 严格按 S0–S7 分阶段引；Langfuse 先用 Cloud 免费层避免自托管 ClickHouse |
| **Dagster 学习曲线陡** | 资产概念与 task 模型不同 | 先做最小资产图；若不适应可换 Prefect 3（迁移成本真实存在，别来回换） |
| **dbt 与"拖拽画布"的关系被误解** | 画布编译成 dbt，不是取代 dbt | 明确：画布 = 易用前端；dbt = 工程底座 |
| **⚠️ 编排绕过权限**（v1 已提，v2 同样适用） | AI 算子会把数据喂给 LLM，风险更大 | ① 编排读源过同一裁剪器 ② 产物继承来源行权 ③ 默认仅创建者可见 ④ 审计带 flow_id ⑤ **AI 算子的 prompt 里不得包含越权行的样例值**（v1 修过的 P0 同类问题） |
| **LLM 成本** | AI 算子 + 归因 + 打标都烧 token | 模型路由（规划用 reasoner、打标用便宜模型）+ 结果缓存 + 批量并发 + 成本看板 |
| **DuckDB 与 PG 双引擎心智负担** | 何时用哪个 | 定规则：能下推 PG 就下推；DuckDB 只用于复杂算子与 Parquet/文件场景 |
