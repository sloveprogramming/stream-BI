## 1. 前提：数据面已经不是瓶颈

`backend/app/sync/erp_autosync.py` 是**整库自动搬运**模式：

- 扫描 ERP(MySQL) `information_schema` 全部 BASE TABLE；
- 有主键的表自动创建 `SyncTask`（上限 `erp_autosync_max_tables=100`，防误配）；
- 增量字段自动识别（`modified` / `update_time` / `gmt_modified`…），识别不到退化为全量比对；
- 新表 → 自动建任务 → cron 拉取 → ods 表 → `discovery` 自动注册数据集 → SSE 推前端（秒级可见）。

**推论**：不需要再问「能接什么业务」—— ERP 里的表已经全都在中台了。
真问题变成两个：

1. **谁来消费**（四个出口通道各接谁）；
2. **现有孤立脚本怎么收敛**（口径与审计的一致性）。

---

## 2. 四类出口 × 业务结合点

### 通道 A：MCP 工具 —— 接 AI 智能体（最有差异化）

| 结合对象 | 场景 | 依赖 |
|---|---|---|
| 畅通园丁（钉钉群机器人） | 群里问「德清仓上周发了多少货」，机器人调 `query_dataset` 直接出数 | 畅通园丁已接 DeepSeek；需加 MCP 工具调用 |
| Dify / Coze 工作流 | 工作流里挂一个「查 ERP 数据」节点 | 平台侧无开发量 |
| 自建 Agent | 任何需要实时业务数据的智能体 | MCP Python SDK |

**为什么这条最值**：同时拥有「一个正在跑的钉钉群 LLM 机器人」和「一个带权限的 ERP 数据中台」的人不多，两者一接就是「聊天里直接查业务数据」，而且权限口径与 Web/API 完全一致（这是设计文档 §4.5 的原意）。

⚠️ 前置：`mcp_tools.py:9` 用 `get_effective_grant`（无管理员兜底）、`mcp_list_datasets` 忽略用户直授 —— 这两个 bug 不修，管理员/直授用户在 MCP 通道会被拒。

### 通道 B：Web 数据助手 —— 业务自助问数

| 角色 | 典型问题 | 现状卡点 |
|---|---|---|
| 仓管 / 物流 | 「本仓这批发货明细」 | 依赖新建 `dataset_grants` 行级规则 |
| 客服 | 「这个订单现在什么状态」 | 无 |
| 销售 / 运营 | 「主力营这个月销售」 | 现在靠 `save_server.py` + `dws.js` 手工链路，可整体替换 |
| 老板 / 管理层 | 跨仓跨区域汇总 | **管理员在 MCP/报表通道被拒（P0 bug）** |

**行级权限 = 现成的组织隔离器**，不需要写代码：

```json
{"field": "warehouse", "op": "eq", "value": "德清"}     // 各仓只看到自己仓
{"field": "supplier",  "op": "eq", "value": "XX食品"}    // 财务只看自己负责的供应商
{"field": "region",    "op": "eq", "value": "华东"}      // 销售按区域
```

### 通道 C：定时报表 —— 财务 / 销售

| 业务 | 报表内容 | 价值 |
|---|---|---|
| 物流对账 | 各仓账单 vs 运单差异明细，每日固定时间生成 | 替代人工跑脚本 + 手工发文件 |
| 财务应付 | 月度应付账款明细（按供应商裁剪） | 导出带审计日志，合规刚需 |
| 销售运营 | 主力营关键数据表（当前靠人工回填钉钉在线表格） | 去掉中间的手工环节 |

`ReportTask` / `ReportRun` 模型与 `/api/reports` 已就绪，支持导入导出 + 权限裁剪 + 水印 + 留存期。

⚠️ 前置：`reports/service.py:27` 同样用了 `get_effective_grant`，报表 owner 是管理员时会直接失败。

### 通道 D：系统 API —— 收敛现有自动化服务

这是**最被低估、见效最快**的一类。服务器上现在跑着一批各自直连数据库的脚本：

| 现有服务 | 现状 | 接中台后 |
|---|---|---|
| `logistics-recon`(8888/8889) | 直连 ERP 拉账单做对账 | 改读中台 API，口径统一 |
| `bom-query` | 直连查 BOM | 同上 |
| `pistachio-agent` | 直连 | 同上 |
| `repair-system` | 直连 | 同上 |
| `save_server.py`(8731) | 配合 Edge 扩展回填钉钉表格 | 中台出数 + API 回填 |
| 竞品数据采集（松子类目） | 采集后独立存放 | 注册为数据集，与 ERP 销售数据同权限体系下对比 |

**一个中台替代 N 个直连脚本**，收益是：统一口径、统一限流、统一审计、字段白名单集中管理。

## 3. 现有模型没覆盖、但业务上会撞到的

| 缺口 | 业务后果 |
|---|---|
| **只支持单一数据源** | 智聘云(HR)、竞品采集库、BOM 库都接不进来 —— 需要多数据源 connector 抽象 |
| **会话只存浏览器 localStorage** | 业务人员换台电脑，历史全丢；也没法审计对话内容 |
| **无评测集** | 说不清「问数准不准」，不敢放到业务群里用 |
| **样例数据绕过行级权限** | prompt 里可能带进越权行的真实值，被模型复述 |

---

## 4. 不该接的业务（明确边界）

| 场景 | 原因 |
|---|---|
| 秒级实时（库存扣减、实时看板） | 设计明确「不做实时」，默认 15 分钟增量 |
| 写回 ERP | 设计明确「只读」，中台永不向 ERP 写入 |
| 敏感个人数据（HR 薪酬、身份证号） | 现权限模型是行级+列级，但审计不展示对话正文，合规需重新设计 |
| 当数仓做大数据分析 | PG 单机 + `assistant_max_rows=1000` 上限，不是 OLAP |

## 5. 两种定位，决定后面怎么改

| | 定位 A：内部唯一取数入口 | 定位 B：可复制的产品/作品 |
|---|---|---|
| 目标 | 公司内所有取数都走中台 | 同类食品/快消电商公司可复用 |
| 关键动作 | 收敛 6+ 个直连脚本；给各角色配行级规则；修 P0 权限 bug | 多租户隔离 + 多 ERP connector（聚水潭/管家婆/金蝶）+ 自助开通 |
| 硬指标 | 替代了几个脚本、几个真实用户在用 | 评测集准确率、可迁移的 ERP 适配数 |
| 风险 | 对外讲故事弱（「我做了个内部工具」） | 离产品化还很远，容易半途 |

**建议：A → B 顺推。** 先在内部跑出真实用户和数据（这是最稀缺的），再把已验证可复用的部分抽象出来，产品故事自然就有了。不要反过来先做多租户。

---

## 6. 若要落地，优先级

1. **修 P0 四处权限口径** —— 不修则通道 A/C 对管理员直接不可用，B 有越权风险；
2. **选一个出口做闭环**（建议通道 D 的 `logistics-recon` 或通道 A 的畅通园丁，二选一）—— 有一个真实用户跑起来，比铺四个半成品强；
3. 给该业务配好 `dataset_grants` 行级规则；
4. 攒 20~50 条真实业务问题做评测集，量化问数准确率；
5. 再横向复制到其他业务线。
