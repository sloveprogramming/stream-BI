## 一、一句话看懂这个平台

> **把 ERP 的数据搬进来，管好谁能看哪部分，然后从五个出口安全地发出去。**

平台只有**一条主动脉**，其余全是挂在这条动脉上的能力：

```
   源数据  ──搬──▶  数据集  ──管──▶  权限  ──发──▶  五个出口
   (ERP)            (ods)          (行级+字段)      (Web/API/MCP/问数/编排)
```

觉得乱，是因为**能力是横向叠加的**，而这条动脉从来没被画出来过。
下面把它画出来。

## 三、四条主干流程

### 流程 1：数据进来（接入）

![数据进来](../docs-diagrams/02-数据进来.png)

```mermaid
sequenceDiagram
    participant SCH as 调度器
    participant AUTO as erp_autosync
    participant ERP as ERP MySQL
    participant PULL as puller
    participant ODS as ods 表
    participant DISC as discovery
    participant DS as datasets

    Note over SCH: 每 5 分钟 + 启动时
    SCH->>AUTO: 触发扫描
    AUTO->>ERP: 读 information_schema（只读）
    Note right of ERP: ★ 对 ERP 只有 SELECT
    AUTO->>AUTO: 新表？建 SyncTask<br/>识别增量字段
    AUTO->>PULL: 派发同步任务
    PULL->>ERP: SELECT ... WHERE 水位线
    ERP-->>PULL: 增量行
    PULL->>ODS: UPSERT 写入本地 PG
    Note over SCH: 每 10 秒
    SCH->>DISC: 扫描 ods 新表
    DISC->>DS: 注册为数据集
    Note over DS: 前端几秒内可见
```

**这一步的两个设计取舍**（都写在代码注释里）：
- **只加列不删列**：ERP 删字段只告警，不自动删本地列（删了会丢数据）
- **类型不一致只告警**：不自动 `ALTER TYPE`（存量数据转换失败会阻塞整个同步）

### 流程 2：谁来管（权限全生命周期）

![权限生命周期](../docs-diagrams/03-权限生命周期.png)

```mermaid
stateDiagram-v2
    [*] --> 无权限
    无权限 --> 申请中: 提交申请<br/>(理由必填)
    无权限 --> 生效中: 管理员直建

    申请中 --> 已拒绝: 管理员拒绝<br/>(理由必填)
    申请中 --> 已取消: 申请人撤销
    申请中 --> 生效中: 管理员批准<br/>(自动落成授权)

    生效中 --> 已过期: 到期任务<br/>每小时扫
    生效中 --> 已撤销: 管理员撤销<br/>(不删记录)

    已拒绝 --> [*]
    已取消 --> [*]
    已过期 --> [*]
    已撤销 --> [*]

    note right of 生效中
        判定三条件：
        ① status = active
        ② 未过 expires_at
        ③ 与数据集同租户
    end note
```

**三个刻意的约束**：
1. **不能自批**自己的申请 —— 否则申请流形同虚设
2. **过期不删记录** —— 审计要能回答"这个人曾经有过什么权限"
3. **跨租户授权一律拒绝** —— 即使数据库里有这条记录

### 流程 3：数据加工（编排）

![数据加工](../docs-diagrams/05-数据加工.png)

```mermaid
flowchart LR
    A["画布拖拽<br/>React Flow"] --> B["FlowDSL<br/>JSON"]
    B --> C{"validate<br/>算子/参数/指标<br/>存在吗"}
    C -->|不通过| A
    C -->|通过| D["compile_flow"]

    D --> D1["源节点 → 带行级权限<br/>WHERE 的子查询"]
    D1 --> D2["算子层<br/>拿不到裸表名"]
    D2 --> E["dbt model<br/>落盘"]

    E --> F["dbt build"]
    F --> G[("物化表<br/>dwd/dws/ads")]
    G --> H["注册数据集<br/>+ 继承行权"]
    H --> I["LineageEvent<br/>血缘"]
    H --> J{"行级规则字段<br/>在产物里吗"}
    J -->|不在| K["强制 owner-only<br/>禁止分享"]
    J -->|在| L["可分享"]

    style D1 fill:#ffe6cc,stroke:#d79b00,stroke-width:2px
    style K fill:#f8cecc,stroke:#b85450
```

**这条流程最重要的性质**：编排在**结构上不可能绕过权限**。
因为源节点被替换成带 WHERE 的子查询，算子层连裸表名都拿不到。

`J` 那个分支是防后门的：如果按 `warehouse` 限权但流程把 `warehouse` 列丢了，
就不能分享产物——否则 owner 能把自己看不到全貌的数据分享出去。

**五个出口共用同一个裁剪器**——这是"同一问题、同一权限、同一结果"的架构保证，

## 四、三条值守流程（定时在后台跑）

![值守任务](../docs-diagrams/06-值守任务.png)

```mermaid
flowchart TB
    subgraph SCHED["APScheduler（6 套任务）"]
        T1["同步任务<br/>sync_*"]
        T2["数据集发现<br/>每 10 秒"]
        T3["ERP 自动同步<br/>每 5 分钟"]
        T4["报表任务<br/>report_*"]
        T5["指标监控<br/>monitor_*"]
        T6["质量巡检<br/>quality_*"]
        T7["授权到期<br/>每小时"]
    end

    T1 & T3 --> ING["数据接入"]
    T2 --> ING
    T4 --> RPT["生成报表文件<br/>按 owner 授权裁剪"]
    T5 --> MON["跑指标 SQL<br/>统计基线判定"]
    T6 --> QUA["三类检查<br/>新鲜度/行数/空值率"]
    T7 --> EXP["过期授权置 expired"]

    MON -->|命中异常| AGENT["Agent 归因<br/>生成简报"]
    QUA -->|命中异常| AUD["审计"]

    style MON fill:#fff2cc
    style QUA fill:#fff2cc
```

**监控与巡检的区别**（容易混，但设计上是刻意分开的）：

| | `monitor_*` | `quality_*` |
|---|---|---|
| 回答 | "这个指标为什么不对" | "这批数到了吗/少了吗/空了吗" |
| 成本 | 命中异常才调 LLM 归因 | 纯 SQL，几乎零成本 |
| 输出 | Agent 简报草稿 | 巡检结果 + 审计 |
| 频率 | 按业务节奏（每天/每周） | 每天都能跑 |

## 六、为什么会觉得乱 —— 诊断

我把 `乱` 拆成四个具体原因，都能对应到实际代码：

### 1. 能力是"叠加"的，不是"分层"的

27 张表里，有 **11 张是后加的能力表**（monitor / quality / lineage / grant_request / tenant / provider / eval…）。
它们都挂在同一个平面上，没有明确的"层"边界。

**但实际上是有层的**——只是没人画出来：

| 层 | 内容 | 表 |
|---|---|---|
| **数据层** | 搬运与加工 | `sync_tasks` `sync_history` `data_flows` `flow_runs` |
| **权限层** | 谁能看什么 | `users` `roles` `datasets` `dataset_grants` `grant_requests` `tenants` |
| **元数据层** | 口径与血缘 | `metrics.yml`(文件) `lineage_events` `verified_qa` |
| **运行层** | 调度与观测 | `monitor_*` `data_quality_*` `report_*` `agent_*` |
| **凭证层** | 审计与密钥 | `audit_logs` `api_keys` `ai_llm_cache` |

按这个分，27 张表立刻变成 5 组，每组 3-6 张。

### 2. 命名不统一，同类东西有两个名字

| 实际是两个东西 | 名字看起来像一类 |
|---|---|
| `sync`（搬数据） | `flow`（加工数据） |
| `monitor`（指标异常→归因） | `quality`（数据体检） |
| `report_tasks`（定时出文件） | `flow`（定时出表） |

**建议**：不改代码，但**在文档和界面上统一措辞**。
比如界面上把 `sync` 叫"数据接入"、`flow` 叫"数据加工"，
`monitor` 叫"指标监控"、`quality` 叫"质量巡检"。

### 3. 五条出口散落在五个文件里

```
app/api/data_api.py          → Web 查询
app/api/export_api.py        → 导出
app/mcp_tools.py             → MCP
app/assistant/chat_api.py    → 问数
app/flow/compile.py          → 编排
```

它们**逻辑上是同一个东西的五个面**，但物理上分散。
这是合理的（关注点分离），只是需要一张图说明"它们都走同一个裁剪器"。

### 4. 三套"权限"概念容易混

| 名字 | 管什么 | 在哪 |
|---|---|---|
| `is_admin` | 租户**内**的管理权 | `users.is_admin` |
| `is_superadmin` | **跨租户** | `users.is_superadmin` |
| `DatasetGrant` | 数据集**行级+字段级** | `dataset_grants` |

前两个是"能不能做管理动作"，第三个是"能看到哪些行/列"。**两者正交。**
