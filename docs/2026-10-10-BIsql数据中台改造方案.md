# BIsql 数据中台改造方案（梳理稿）

> 日期：2026-10-10
> 状态：**待评审**（本稿只梳理思路，未动任何代码）
> 定位变化：从「数据分发中台」升级为「面向业务人员的数据中台」
> 新增诉求：① 算子库 + 可拖拽数据编排（过滤/去重/映射…）② 数据治理 ③ 监控看板 ④ 服务对象 = PMC / 运营 / 销售 / 采购

---

## 0. 结论先行

**一句话判断**：你现在手上的 BIsql 已经是一个合格的「数据分发中台」（采集 ✅ 存储 ✅ 权限 ✅ 出口 ✅），缺的是**三个层**：

| 缺什么 | 业务语言 | 一句话 |
|---|---|---|
| **加工层** | 「我要的数据要能自己拼出来」 | 算子库 + 拖拽编排，把 ods 原始表加工成业务口径的宽表 |
| **治理层** | 「这个数是谁的、怎么算的、准不准」 | 元数据 / 血缘 / 指标口径 / 质量规则 |
| **运营层** | 「我打开就能看、能自己取」 | 面向角色的看板 + 自助取数入口 + 质量/运维大盘 |

**最关键的一个判断**：这三层**不要另起炉灶**，全部长在你已有的两块资产上——
- **ods 贴源层** → 是编排层的输入，也是血缘的起点；
- **权限裁剪器（一套喂四个出口）** → 是编排层的护栏，**编排产物必须仍然走同一个裁剪器**，否则等于开了后门绕过权限，整个项目最核心的差异化就废了。

**最大的坑（先说）**：业务人员（PMC/运营/销售/采购）要的**不是**数据中台的治理功能，而是"我要的那批数、按我的口径、现在就能拿到"。治理和监控看板是**给中台自己（IT/数据 owner）用的**，不是给业务看的。**把内部运维大盘当业务价值交付，是数据中台最常见的死法**——做了几十个监控图，业务一个都不用，因为业务从来不看"数据质量得分"。

## 2. 差距分析：数据中台的能力矩阵

对照市场公认的数据中台能力矩阵，逐项打分（✅已有 / 🟡部分 / ❌缺）：

| 能力域 | 必备子能力 | 你的现状 | 差距 |
|---|---|---|---|
| **采集集成** | 多源接入、批/流、CDC | 🟡 只有 ERP 单源（MySQL），批量 | 多源 Connector（竞品库/BOM/物流账单/HR） |
| **存储分层** | ODS/DWD/DWS/ADS 分层 | 🟡 只有 ODS | 缺加工层（编排产物落哪） |
| **开发编排** | 可视化 DAG、算子库、调度、版本 | ❌ 无 | **本次主攻** |
| **元数据** | 技术/业务元数据、数据地图 | 🟡 技术元数据有（datasets/ds.columns） | 业务元数据（中文名/owner/口径/标签/敏感级） |
| **血缘** | 表级 + 字段级血缘、影响分析 | ❌ 无 | 编排 DAG 天然是血缘源（白捡） |
| **标准/指标** | 指标字典、命名规范、枚举字典、主数据 | 🟡 语义层有规划（metrics.yaml） | 需落地 |
| **质量** | 六维度规则、稽核、工单闭环 | ❌ 无 | 做成「质量算子」内嵌编排 |
| **安全权限** | 行级/列级/脱敏/审计 | ✅ 强项，市场领先 | 编排产物须继承 |
| **服务/API** | 数据服务、订阅、SLA | ✅ 有 API/MCP | 服务订阅、SLA 看板 |
| **资产运营** | 资产目录、调用排行、健康度 | ❌ 弱 | 运营看板 |
| **业务自助** | 自助取数、看板、问数 | 🟡 问数有 | 自助看板缺失 |

**差距集中在：编排（❌）、血缘（❌）、质量（❌）、业务自助看板（🟡）。** 这四块正好是你这次的需求。

## 3. 市场主流做法调研（2026-10 查证）

### 3.1 数据治理：主流方法论

| 方法论/产品 | 核心思想 | 对你可抄的点 |
|---|---|---|
| **阿里 OneData + 瓴羊 Dataphin** | "书同文、车同轨"：统一指标定义、统一数据域划分、统一模型规范，消除跨部门口径二义性。核心理念**"治理即研发"**——把数据标准、质量规则、安全策略**内嵌进研发流程**，而不是事后检查 | ① 指标口径先行（雅戈尔案例：仅"营收金额"一项口径不统一，每天偏差数十万）② 质量规则绑到任务上，异常自动阻断 ③ 命名规范建表时自动校验 |
| **阿里 DataWorks** | 一站式：DataStudio 在线 IDE 支持拖拽工作流 + 代码编辑；数据地图/血缘突出；Data Agent 用自然语言驱动 | 拖拽编排 + 血缘 + AI 三件套的产品形态就是行业标配 |
| **腾讯 WeData** | Data+AI 一体化，实时集成链路**数据对账**（监控来源表与目标表差异）；基于 VS Code 架构统一开发环境 | "源头 vs 目标对账"这个思路直接可用（你已有全量哈希比对，可复用做对账看板） |
| **帆软 FineDataLink** | DAG 可视化编排 + 治理融进流程：拖拽画布做去重/空值填充/格式标准化/拆分合并；元数据管理+血缘+质量监控+安全管控一体 | **最贴近你要做的形态**（拖拽清洗算子），也是"一体化而非多工具拼装"的代表 |
| **华为 DataArts** | 信创合规、字段级权限、自动脱敏 | 字段级权限你已有 |

**市场共识（对你有直接影响）**：
1. **数据中台失败的第一原因不是技术，是口径不统一**。技术做了，业务不认账。→ 指标字典必须先于编排铺开。
2. **"治理即研发"**：治理不能事后补。→ 把质量校验做成编排里的一个算子节点，编排时就校验，而不是上线后跑质量报告。
3. **从"人找数据"到"数据找人"**：资产目录 + 主动推送。→ 你已有主动监控 Agent，方向对。
4. **一体化 > 多工具拼装**：链路割裂的隐性成本（多产品授权/多团队运维）让企业退回一体化。→ 别引入 Airflow/DolphinScheduler/Spark 一堆中间件。

### 3.2 监控看板：主流做法

**黄金四信号**（Google SRE，被普遍扩展到数据中台）：延迟、流量、错误、饱和度。

**看板分层（关键：一个看板服务所有人 = 失败）**：

| 层 | 看什么 | 给谁看 | 频率 |
|---|---|---|---|
| **基础设施层** | PG 连接数/慢查询/磁盘/CPU | IT/你自己 | 实时告警 |
| **流水线层** | 任务成功率、延迟、积压、重试次数 | IT/数据开发 | 日 |
| **数据质量层** | 六维度得分、规则通过率、异常工单 | **数据 owner** | 日 |
| **资产运营层** | 资产覆盖率、调用量排行、活跃用户、健康度指数 | 管理 + 数据运营 | 月 |
| **业务价值层** | 按角色的业务看板（PMC 缺料、运营日报…） | **业务人员** | 日/实时 |

**质量六维度（ISO 8000 / DAMA，行业标准）**：

| 维度 | 度量公式 | 典型阈值 |
|---|---|---|
| 完整性 | (总记录数 - 空值记录数) / 总记录数 | ≥95%（视字段） |
| 唯一性 | (总记录数 - 重复记录数) / 总记录数 | 100%（主键） |
| 有效性 | 符合约束的记录数 / 总记录数 | ≥99% |
| 准确性 | 准确记录数 / 总记录数 | ≥99% |
| 一致性 | 一致记录数 / 比对记录数 | ≥99% |
| 及时性 | 及时产出任务数 / 总任务数 | ≥98% |

**资产健康度指数**（行业模板）：质量 30% + 时效 25% + 完整 25% + 安全合规 20%，红黄绿三色，跌破阈值自动预警。

**SLA 四要素**（质量阈值 ≠ SLA）：①各维度阈值 ②测量频率与告警方式 ③谁接告警、最长响应时间 ④修复流程与工单关闭标准。

**你该抄的**：六维度规则 → 做成质量算子；健康度指数 → 资产看板一个数字；SLA 四要素 → 给每个数据集挂 owner 和阈值。
**你不该抄的**：桑基图/热力矩阵/12 个月趋势曲线那套"运营大屏"——单机自用、百人规模，做了没人看。

## 4. 改造一：算子库 + 可拖拽数据编排（核心）

### 4.1 目标形态

```
        画布（前端）            → 拖拽算子、连线、配置参数
              ↓  保存
        流程定义（DSL JSON）    → nodes[] + edges[]，版本化落库
              ↓  编译
        执行计划（DAG）          → 拓扑排序、依赖检查、并行度
              ↓  执行
        引擎（SQL 下推 / 兜底）  → 在 PG 内跑，结果物化
              ↓  注册
        数据集（datasets）      → 自动注册，继承权限，可被四出口消费
```

**核心设计原则**：**编排的产物不是"一份文件"，而是一个新的数据集**。这样它自动进入你现有的 `datasets` 注册表 → 自动被权限裁剪器管住 → 自动可被 API/MCP/问数/导出消费。**零额外开发就获得了权限、审计、四出口能力。**

### 4.2 分层：编排产物落到哪

沿用国内标准数仓分层命名（面试和业务方都认）：

| 层 | 含义 | 数据从哪来 | 谁维护 |
|---|---|---|---|
| **ODS** | 贴源，原样搬运 | ERP | 同步引擎（已有） |
| **DWD** | 明细清洗（去重、类型规范、字段映射、异常过滤） | ODS + 编排 | 业务+IT 共建 |
| **DWS** | 轻度汇总（按主题聚合，如"日×仓×SKU"） | DWD + 编排 | IT |
| **ADS** | 应用层（直接喂看板/报表的宽表） | DWS + 编排 | IT+业务 |
| **数据集（datasets）** | 出口视图，挂权限 | ODS/DWD/DWS/ADS 均可注册 | 权限管理员 |

→ PG 里新建 `dwd` / `dws` / `ads` 三个 schema，与现有 `ods` 并列。

### 4.3 算子库设计

**分七类，最小可用集 12 个算子即可跑通闭环，全量约 28 个。**

| 类别 | 算子 | 说明 | MVP |
|---|---|---|---|
| **① 输入** | 读取数据集 / 读取ERP表 / 读取文件(CSV·Excel) / 自定义SQL | 流程起点 | ✅ 读取数据集 |
| **② 字段处理** | 字段选择 / 重命名 / 类型转换 / 派生字段(表达式) / 拆分合并 | 最常用 | ✅ 选择+重命名+派生 |
| **③ 清洗** | **过滤(条件表达式)** / **去重(按主键·全字段·保留最新)** / 空值填充 / 空值剔除 / 字符串清洗(trim·大小写·去空格) / 日期解析 | 你要的核心 | ✅ 过滤+去重 |
| **④ 关联** | JOIN(inner/left/right/full) / UNION / 维表LOOKUP | 跨数据集拼接 | ✅ JOIN |
| **⑤ 聚合计算** | GROUP BY聚合 / 窗口函数 / 行列转换(PIVOT·UNPIVOT) / CASE WHEN 分箱 | 指标计算 | ✅ GROUP BY |
| **⑥ 质量校验** | 非空校验 / 唯一校验 / 值域校验 / 格式校验 / **跨表对账**(源 vs 目标行数·金额) | 治理内嵌（关键） | 🟡 后置 |
| **⑦ 输出** | 物化到表 / 注册为数据集 / 导出文件 / 发通知 | 流程终点 | ✅ 物化+注册 |

**设计要点**：
1. **每个算子 = 一个纯函数**：`(输入DataFrame/SQL片段, 参数) -> 输出`。这样引擎可替换、算子可单测。
2. **算子参数用 JSON Schema 描述**，前端根据 Schema 自动渲染配置表单——**加新算子不用改前端**。这是能长期维护的关键。
3. **质量算子要能"阻断"**：校验不通过时，可选"告警继续"或"终止流程不落表"。这就是"治理即研发"落地——**脏数据根本进不了 dwd/dws 层**。

### 4.4 执行引擎选型（最关键的技术决策）

**约束**：单人维护、数据在 PG、单机、百人规模、数据量中小（ERP 同步，日增万级到百万级）。**明确不需要 Spark/Flink。**

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. SQL 下推编译** | 把整个 DAG 编译成一条带多层 CTE 的 SQL，在 PG 里执行，结果 `CREATE TABLE AS` | 零新引擎；数据不出 PG；SQL 可读可审计；复用已装的 sqlglot；天然继承只读事务+超时+行数上限 | 复杂算子表达受限 | ✅ **主引擎** |
| **B. 进程内 DataFrame** | Polars / DuckDB 在 Python 进程里跑算子链 | 算子实现自由；DuckDB 还能直读 PG | 数据要出库；内存占用 | ✅ **兜底**（PIVOT/复杂窗口等 A 表达不了的算子） |
| **C. 分布式** | Spark / Flink | 海量数据 | 单人维护灾难 | ❌ **不做** |

**推荐：A 为主 + B 兜底**。理由全在你的实际约束上——单人、单机、PG 已有、SQL 可解释。**不要为了"看起来像大数据平台"引入 Spark。**

**执行细节**：
- 每个算子节点编译成一段 CTE（`WITH step1 AS (...), step2 AS (...)`），最后一条 `CREATE TABLE dwd.xxx AS SELECT ...`；
- 中间结果**默认不落盘**（CTE 内存计算），只在"输出节点"落表——避免一堆中间小表；
- 跑之前先 `EXPLAIN` 一遍，预估代价，超阈值（如全表扫千万行）先告警；
- 复用现有 `statement_timeout` + 行数上限，防止编排拖垮 PG。

### 4.5 前端画布选型

| 方案 | 适配度 | 结论 |
|---|---|---|
| **React Flow** | 你的前端是 React + Ant Design；受控组件架构；Dify / Flowise / LangGraph Studio 等主流编排平台都用它 | ✅ **首选** |
| AntV X6 | 功能更强（内置对齐线/撤销重做/小地图），但学习曲线陡、体积大（~180KB vs ~95KB） | 备选 |
| AntV G6 | 面向"图分析展示"，不是编辑器 | ❌ |

**必备交互**（否则业务/IT 都不愿用）：
- 左侧算子面板分组折叠 → 拖到画布；
- 节点点击弹出配置面板（由 JSON Schema 自动渲染）；
- **连线合法性校验**（如"输出节点不能有出边"、"不能成环"）——Otto ETL 的实践证明这一条能大幅简化代码；
- **每步可预览**（点节点看前 20 行中间结果）——这是拖拽编排的核心体验，没有预览等于盲编；
- 撤销/重做、自动布局、运行日志面板。

### 4.6 编排 DSL 与运行模型

```json
{
  "flow_id": "flow_01J8...",
  "name": "dwd_销售订单_清洗",
  "version": 3,
  "nodes": [
    {"id": "n1", "type": "source.dataset", "params": {"dataset": "ods.sales_order"}},
    {"id": "n2", "type": "clean.dedup",    "params": {"keys": ["order_id"], "keep": "latest", "order_by": "update_time"}},
    {"id": "n3", "type": "clean.filter",   "params": {"expr": "status != '已取消' AND amount > 0"}},
    {"id": "n4", "type": "field.derive",   "params": {"name": "net_amount", "expr": "amount - discount"}},
    {"id": "n5", "type": "quality.unique", "params": {"columns": ["order_id"], "on_fail": "abort"}}
  ],
  "edges": [{"from": "n1", "to": "n2"}, {"from": "n2", "to": "n3"}],
  "output": {"type": "materialize", "target": "dwd.sales_order_clean", "register_dataset": true}
}
```
- 流程定义**版本化落库**（`data_flows` + `data_flow_versions`），可回滚；
- 执行记录落 `flow_runs`（开始/结束/状态/行数/耗时/错误），与现有 `sync_history` 同构——
  **直接复用你已有的同步监控 API 和看板模式**；
- 调度：复用 APScheduler，job 前缀 `flow_`（与 `sync_` / `monitor_` 并列），cron 可配。

### 4.7 与现有资产的复用映射（成本极低的原因）

| 编排需要的能力 | 已有资产 | 复用方式 |
|---|---|---|
| 输入源 | `datasets` + ods 表 | 直接读 |
| 权限护栏 | `access/scoped_query.py` 裁剪器 | 编排读取时**必须先经裁剪器**，见 4.8 |
| SQL 安全 | sqlglot AST 闸门 | 编译产物过同一闸门 |
| 执行上下文 | 只读事务 + timeout + 行数上限 | 原样复用 |
| 产物出口 | `datasets` 注册 + 四出口 | 自动获得 |
| 运行监控 | `sync_history` + 同步监控 API | 同构扩展为 `flow_runs` |
| 调度 | APScheduler | 加 job 前缀 |
| 告警 | `send_alert` webhook | 原样复用 |
| 血缘 | **DAG 的边就是血缘** | 零成本生成 |

### 4.8 ⚠️ 安全红线：编排不能成为绕过权限的后门

**这是本方案第一优先级的技术风险。** 场景：一个只有"德清仓"行级权限的用户，A 用编排把 `ods.sales_order` 全量读出来物化成 `dwd.my_table`，然后 B 通过 `dwd.my_table` 就看全了所有仓 → **权限形同虚设**。

**必须定的四条规定**：
1. **编排读源时必须过裁剪器**：流程执行时的数据读取，按"流程 owner 的有效授权"裁剪，与四出口同一口径；
2. **产物继承来源行的行级规则**：如果流程输入带 `warehouse='德清'` 约束，产物数据集必须带上同样的约束（除非管理员显式放开）；
3. **产物注册数据集时的权限默认最保守**：默认只有创建者可见，需管理员显式授权给他人；
4. **审计要记录"数据来源链路"**：审计日志里带上 `flow_id`，让"这批数是从哪来的"可追溯。

> 一句话：**编排层是权限体系的新入口，必须和另外四个出口一起过同一道闸门，否则前面所有工作的差异化价值归零。**

## 5. 改造二：数据治理

**按优先级排序（先做性价比最高的）：**

### 5.1 指标字典 / 语义层（P0，最高优先级）
- 你在 Agent 方案 Step 5 已规划 `metrics.yaml`（Ossie 风格：`name/display/synonyms/formula/dataset/grain/owner`），**这次必须落地**——它是"口径统一"的载体，也是编排层"派生字段"的口径来源；
- 与编排层联动：编排里算毛利，不要手写公式，而是**引用指标字典里的 `gross_margin` 口径**。这样口径改一处，所有管道跟着变。
- **业务价值**：PMC 说的"缺料"、运营说的"动销"、采购说的"到货及时率"，都能写成唯一口径，跨部门不再打架。

### 5.2 元数据补全（P0）
- 技术元数据已有（`datasets` + 字段清单）；
- **补业务元数据**：中文名、描述、业务域归属、**owner（负责人）**、标签、敏感级别（公开/内部/敏感）、更新频率；
- 这些字段是**看板和资产目录的数据基础**，也是"数据找人"的前提。

### 5.3 血缘（P1，几乎白捡）
- 编排 DAG 的 `edges` 本身就是表级血缘；
- 字段级血缘：从算子的字段映射（选择/重命名/派生）推导；
- 用途：① 变更影响分析（改 ERP 字段，哪些看板会挂）② 资产看板可视化 ③ 面试/汇报的落地亮点。

### 5.4 数据质量（P1）
- 六维度规则（见 3.2 表）→ **做成质量算子**（第 4.3 节第 ⑥ 类），内嵌在编排流程里；
- 规则绑到数据集（`quality_rules` 表：数据集、维度、字段、规则表达式、阈值、失败动作、owner）;
- 定时稽核任务（复用 APScheduler），结果落 `quality_checks`；
- 异常 → 复用 `send_alert` 推送 + 生成工单（可接你已有的钉钉待办能力）；
- **关键**：质量规则要和编排绑在一起跑，而不是离线单独跑报告——这就是"治理即研发"。

### 5.5 数据标准（P1）
- 命名规范（表/字段：层前缀 + 业务域 + 主题，如 `dwd_sales_order_clean`）；
- 枚举值字典（订单状态、仓库代码、商品分类）——**这条直接解决你 09-21 记的"类目映射是运营最大障碍"**；
- 主数据统一（商品SKU、仓库、客户/供应商）——PMC/采购场景的前置依赖。

### 5.6 治理的落地机制（比工具更重要）
- **每个数据集挂 owner**，owner 对质量负责；
- **建数据决策委员会**（雅戈尔案例）——哪怕只是"运营负责人+财务+IT 三人组"，定期审口径变更；
- 指标平均每月迭代是正常的，别指望一次定死。

## 6. 改造三：监控看板

**分四层，明确给谁看**（照抄 3.2 的分层，但按你的规模砍）：

### 6.1 中台运维大盘（给 IT / 你自己）
- 同步健康度：任务成功率、延迟、失败重试次数、上次同步时间；
- 编排健康度：flow_runs 成功率、平均耗时、失败 TOP；
- 基础设施：PG 连接数、慢查询、库大小增长趋势；
- **复用现有同步监控 API**，扩展成前端一个页面即可。

### 6.2 数据质量看板（给数据 owner）
- 六维度得分（雷达图/仪表盘）、规则通过率、异常工单列表、治理前后对比；
- **资产健康度指数**：质量30% + 时效25% + 完整25% + 安全20%，一个数字 + 红黄绿。

### 6.3 资产运营看板（给管理 + 你）
- 资产覆盖率、数据集数量趋势、调用量排行、活跃用户、SLA 达成率；
- 埋点：谁在用什么数据 → 决定下一批该建什么。

### 6.4 业务价值看板（给业务人员）—— 这才是交付给 PMC/运营/销售/采购的
**注意：这一层本质是"低代码 BI"，不是"数据中台监控"。**
- 按角色定制：PMC 看缺料/在途/效期，运营看日销/转化/商品表现，销售看自己的客户/订单/回款，采购看供应商/价格/交期；
- 数据来源：编排产出的 ADS 表 + 现有 `/api/v1/datasets/{ds}/rows`；
- **行级权限天然生效**（销售只看自己区域）——这是你最大的优势，别人做 BI 还要重做一遍权限。

### 6.5 看板实现建议（反过度设计）
- **不要引入 Superset/Metabase 那一套**（多一个服务要维护，权限还要重做一遍）；
- 用现有 React + Ant Design 画，数据走现有 API，**权限自动继承**；
- 图表库用 AntV G2/ECharts（前端已用 Ant Design，生态一致）；
- 第一版只做 4 个看板（每个角色一个），跑两个月看谁在用，再决定加。

## 7. 面向业务人员：角色 × 场景 × 能力映射

| 角色 | 真实痛点 | 需要的编排 | 需要的看板 | 涉及数据源 |
|---|---|---|---|---|
| **PMC**（生产物料控制） | 缺料/断货、在途不透明、临期/效期风险 | 库存 + 在途 + 销售 + 效期 多表 JOIN，算可用库存/周转/临期天数 | 缺料预警、库存健康、效期看板 | ERP 库存 + 采购 + 销售 |
| **运营** | 日报手工拼 Excel ~1h；临时问题排队 1-2 天；不认口径 | 订单去重/清洗 → 按日×渠道×SKU 汇总；类目映射 | 经营日报、商品表现、转化漏斗 | ERP + 生意参谋（需多源） |
| **销售** | 看不到自己客户的完整视图；回款不透明 | 订单 + 客户 + 回款关联 | 个人业绩、客户画像、回款进度 | ERP 订单 + 财务回款 |
| **采购** | 供应商交期/价格波动无监控；到货质量 | 采购订单 + 到货 + 价格历史 → 到货及时率/价格波动 | 供应商绩效、价格趋势 | ERP 采购 + 到货 |

**给业务人员的体验三原则**：
1. **不写 SQL**（拖拽 or 问数）；
2. **不找 IT**（自助）；
3. **看到的是自己那份**（权限自动生效）。

**⚠️ 三个必须先解决的前置障碍**（诚实说，来自 09-21 记录）：
- **类目映射**：运营说的"坚果类/礼盒装"跟 ERP 商品分类编码对不上 → 不建映射则结果运营不认（→ 用枚举字典/主数据解决）；
- **跨库**：GMV 在 ERP、访客数在生意参谋 → 需要多源 Connector；
- **响应速度**：问数等 30 秒运营就不用了 → 编排产物落表（预计算），别让业务等着实时算。

## 8. 落地路线（分期）

**原则：只加不换、一次一档、先能测。**

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **S1 编排地基**（核心，必须先做） | `dwd/dws/ads` schema；`data_flows`/`data_flow_versions`/`flow_runs` 表 + 迁移；算子基类 + JSON Schema 机制；**12 个 MVP 算子**；SQL 下推编译器（DAG→CTE）；`/api/v1/flows` CRUD + 手动运行 | 后端能跑通「读数据集→去重→过滤→派生→物化→自动注册数据集」闭环；产物在四出口可用且权限生效；单测覆盖编译器与每个算子 |
| **S2 画布** | React Flow 画布；算子面板；配置表单自动渲染；连线校验；**每步预览**；运行日志 | 不写代码能拼出一条清洗流程并跑出结果；输出自动出现在数据集列表 |
| **S3 治理-A** | 指标字典落地（metrics.yaml + 加载器 + 编排引用）；元数据补业务字段；血缘（表级+字段级） | 编排派生字段引用指标口径；血缘图能从 ADS 追到 ERP 源字段 |
| **S4 治理-B** | 质量算子（六维度）；`quality_rules`/`quality_checks`；定时稽核 + 告警 + 工单 | 质量规则能阻断脏数据落表；异常自动推送；质量看板有分数 |
| **S5 看板** | 运维大盘 + 质量看板 + 资产看板 + **4 个角色业务看板** | 业务人员能自己打开看到自己的数；行级权限在业务看板上生效 |
| **S6 多源** | Connector 抽象（竞品库/BOM/物流账单/HR） | 至少接入 1 个非 ERP 源，跑通跨源编排 |

**与已有计划的关系**：Agent 改造方案（Step 0-6）已完成到 Step 6 主体，S1-S2 与它**并行不冲突**（编排层在 ods 与出口之间，Agent 层在出口之上）。**建议先做 S1+S2**，因为这是你这次的核心诉求，且能很快给业务看到东西。

## 9. 明确不做（反过度设计）

| 不做 | 原因 |
|---|---|
| Spark / Flink / 分布式计算 | 单人维护、单机、PG 够用，引入即灾难 |
| Airflow / DolphinScheduler / SeaTunnel | APScheduler 满足单机规模，多一个中间件就是多一个要运维的东西 |
| 实时（秒级）流处理 | 项目定位 15 分钟增量，业务也不要求秒级 |
| 通用 ETL 平台（50+ 数据源适配、多引擎） | 那是产品化需求（Dataphin/DataWorks 的战场），你是内部自用 |
| 通用 RAG 聊天机器人 | 同质化 |
| 炫酷运营大屏（桑基图/3D/热力矩阵） | 是"运营"不是"价值"，做了没人看 |
| AI 自动生成整条数据管道 | 先做人工编排，验证价值再谈 |
| 自研 DSL 格式 | 用 JSON + JSON Schema，别自创规范 |
| 把中台运维大盘当业务价值交付 | 业务不看数据质量得分 |

## 10. 风险与边界

| 风险 | 说明 | 应对 |
|---|---|---|
| **⚠️ 编排绕过权限** | 最高优先级技术风险（见 4.8） | 四条硬规定，写在设计文档里当验收项 |
| **业务人员不会用拖拽** | 拖拽编排对 PMC/运营仍有门槛 | 双入口：拖拽给 IT/数据熟练者，**问数 + 模板**给业务；预置常用模板（如"日销汇总"）一键套用 |
| **口径仍然打架** | 工具给了，人不认账 | 先落地指标字典 + 挂 owner + 建小委员会（5.6） |
| **做成了没人用的看板** | 最常见死法 | 第一版只做 4 个角色看板，两月后看使用数据再扩 |
| **PG 被编排跑挂** | 大流程全表扫 | EXPLAIN 预估 + timeout + 行数上限 + 中间结果不落盘 |
| **单人维护压力** | 能力越加越多 | 严格锁 MVP 算子集；算子=纯函数，可单测；每层只做一件事 |
| **与 ERP 边界** | 别变成"再做一个 ERP 报表中心" | 判定标准（沿用 09-22 结论）：ERP 报表能搞定且不需跨源/分发/权限 → 别加；做不到才加 |

## 11. 待确认项

1. **多源优先级**：竞品库 / BOM / 物流账单 / HR，先接哪个？（运营场景缺"生意参谋"，PMC 缺"在途/效期"）
2. **业务方真实样本**：能不能找 PMC/运营各要一份「现在的日报模板 + 一周临时取数记录」？——这是决定该建哪些数据集、哪些口径、哪些行权规则的最有效输入（09-21 结论）。
3. **编排的使用者是谁**：IT 自己用（那就先做后端 + 简单 UI），还是业务人员直接用（那 S2 画布必须做到零门槛 + 模板）？
4. **权限放开策略**：编排产物默认只有创建者可见，是否需要"部门内共享"这一层？
5. **指标字典范围**：先覆盖哪些指标？（建议先做 PMC+运营共 10 个高频指标，跑通再扩）
6. **看板技术路线**：确认自研（复用现有 React + 权限）而非引入 Superset/Metabase。

## 附：一句话总结

**你这个项目的底座（采集+权限+四出口）已经很硬，这次要补的是「加工层（算子编排）、治理层（口径+质量+血缘）、运营层（角色看板）」三层。三层全部长在现有权限裁剪器上——编排是新的入口，所以编排必须过同一道权限闸门，这是本方案的第一红线。技术上不引入任何重中间件：SQL 下推 + React Flow，单人可维护。业务价值不在监控大屏，而在 PMC 的缺料预警、运营的日销看板、销售的回款进度、采购的供应商绩效——四个角色，四个看板，先跑两个月看谁在用。**
