# Proposal: 指标字典（口径唯一来源）

## Why

编排已经能产出表了，但**同一个指标在不同地方算出不同的数**——这是数据中台最常见的死法：

- 运营说的「销售额」是支付口径，财务说的是回款口径；对不上就人工核对，
  核对结论只留在聊天记录里，下次再对一遍；
- 编排里的派生字段目前是裸表达式（`amount - discount`），口径散落在每条流程里，
  改一处要翻遍所有流程，还容易漏；
- 问数 Agent 被问「上月销售额」时只能猜口径，答错了也没人会发现。

这三件事的根因是同一个：**口径没有被当作一等公民管理**。
技术做了，业务不认账，中台就只是「更贵的 ETL」。

## What Changes

- 把指标定义沉淀为 dbt 语义模型（MetricFlow 格式），每个指标包含
  名称、展示名、同义词、计算公式、所属数据集、粒度、负责人；
- 编排的「派生字段」算子可以**引用指标口径**，而不是手写公式；
- 问数链路在生成 SQL 前先做**指标对齐**，把口径注入上下文；口径歧义时反问而不是猜；
- 指标定义随 dbt 项目版本化，任何改动都体现为一次可评审的代码变更。

## Capabilities

### New Capabilities

- `metric-dictionary`: 指标口径的定义、校验、检索、被编排引用、以及问数前的口径对齐

### Modified Capabilities

- `data-flow`: 「派生字段」算子新增「引用指标口径」的行为（原需求只支持裸表达式）

## Impact

- 新增 `backend/dbt/models/marts/metrics.yml`（指标定义本体）
- 新增 `backend/app/metrics/`（加载、校验、检索、渲染口径）
- 改动 `backend/app/flow/operators/field.py`（`field.derive` 支持指标引用）
- 改动 `backend/app/flow/compile.py`（编译期展开指标为公式）
- 改动 `backend/app/assistant/prompts.py`（问数前注入指标口径）
- 改动 `backend/dbt/dbt_project.yml`（如语义模型需要额外配置）
- **不新增运行时依赖**：MetricFlow 随 dbt-core 一起安装，已在本机验证可 import

## 不做什么（Out of Scope）

- **不做指标的可视化编辑器**。指标定义由人写（AI 可以代写草稿），
  先把口径统一起来；有了稳定需求再考虑 UI。
- **不做指标的实时计算**。仍然走编排物化（T+1 / 定时），
  本项目的既有定位就是 15 分钟级增量，不做实时。
- **不引入独立的语义层服务**（Cube / AtScale / dbt Cloud）。
  多一个进程要维护，且本项目强调「不自研格式、也不多引中间件」。
- **不做指标血缘**。指标 → 数据集 → 源表的影响分析属于血缘能力，
  后续单独提一个 change，不塞进这里。
