# Proposal: 质量校验算子（quality.assert）

## Why

数据中台的「治理」里最反复出现的一句话是：**"这个数不对，但不知道从什么时候开始不对的。"**
脏数据不是被拦下来的，是流到报表上才被人发现的 —— 那时已经过了 N 道加工。

既有的 `clean.dedup` 解决"重复"，`clean.filter` 解决"我不要这些行"，
但都没有回答"**这些行合不合格**"。质量规则如果做成事后的检查脚本，
就又回到了"治理归治理、研发归研发"两张皮 —— 本项目从立项起就反对这个（"治理即研发"）。

把质量校验做成**画布上的一个算子**，让它在数据流程的任意位置生效：
源头上标一次、加工后再标一次，违规行带着原因流向下游 —— 谁污染的、脏在哪一行，有据可查。

## What Changes

- 新增 `quality.assert` SQL 算子，覆盖质量六维度里画布能表达的三类：
  **完整性**（`not_null`）、**唯一性**（`unique`，支持组合键）、**有效性**（`rules`，值域/格式）；
- 输出 `qa_passed`（是否通过）+ `qa_reason`（违规原因，可读中文描述）两列，
  **不删行、不中止** —— 要挡住脏数据，下游接一个 `clean.filter(qa_passed)` 即可（与
  `dedup.semantic`「标记不删行」同一设计哲学）；
- 纯 SQL 实现（CASE WHEN + CONCAT_WS + 窗口函数），可进 dbt 编译与物化，
  **不需要任何 AI 调用** —— 质量校验是规则，不是判断；
- 前端零改动：算子目录走 JSON Schema 自动渲染表单（这套设计的第一次直接回报）。

## Capabilities

### New Capabilities

- `quality-assert`：数据质量校验算子，行级标记违规与原因

### Modified Capabilities

- （无）`data-flow` 既有契约不变：新增算子不改变流程语义与权限模型。

## Impact

- 新增 `backend/app/flow/operators/quality.py`（算子本体，engine=sql）
- 改动 `backend/app/flow/operators/__init__.py`（注册）
- 改动 `backend/scripts/flow_smoke.py`（冒烟加一条质量流程：违规行被标记、行数不变）
- **不新增表、不新增依赖、不改前端**

## 不做什么（Out of Scope）

- **不做"违规即中止流程"模式**。删行/中止都是不可逆动作，标记是可解释的；
  想挡住脏数据就接 `clean.filter` —— 画布连线本来就是这么用的。
- **不做汇总报告表**（按表/按规则的通过率聚合）。行级标记有了，汇总在下游用
  `agg.group` 就能算；专门的质量报告等 GA/看板阶段一起做。
- **不做六维度全量**：及时性（要水位线元数据）、一致性（要跨表比对）依赖还没有的基建，
  先落画布能表达的三类；`quality.assert` 的参数结构给未来维度留了加法空间。
- **不做自定义 SQL 谓词**（用户写裸 SQL 片段当规则）。表达式注入的口子不开，
  结构化参数覆盖不了的场景等真实需求出现再设计。
