# Design

## Context

血缘的边**已经存在**，只是没人组织：

| 边 | 数据在哪 |
|---|---|
| 流程输入 → 产物 | `data_flow_versions.input_datasets`（每版流程）+ `data_flows.target_schema/target_table` |
| 数据集 → 物理源表 | `datasets.source_table`（如 `ods.sales_order`） |
| 运行记录 | `flow_runs`（run_id、状态、时间） |

所以本 change 的大部分工作是**组织与暴露**，不是采集。

**复用的现有模块**：

- `app/flow/runner.py` 成功路径 —— emit 点（`register_output_dataset` 之后）
- `app/models/flow.py::DataFlowVersion.input_datasets` —— 流程输入
- `app/models/access.py::Dataset.source_table` —— 物理源
- `app/api/deps.py::get_principal` —— 登录即可查（不要求授权，见决策 2）

## Goals / Non-Goals

**Goals:**

- 每次成功运行落一条标准 OpenLineage 事件（将来接任何血缘工具都认）
- 任意数据集双向追溯，防环、防重复
- 前端数据集详情页看得到上下游

**Non-Goals:** Marquez/DataHub、问数血缘、AI 中间表、交互式 DAG 图（见 proposal）

## Decisions

### 决策 1：事件在「成功路径」emit，与运行记录同一事务落库

`run_flow` 的 `status = "ok"` 分支里构造事件、加进 session，
随 `finally` 的 `session.commit()` 一起落库。

**为什么不在 dbt 回调/异步发**：单机平台没有消息总线，异步只会引入"事件丢了"的新问题；
同一事务保证**事件与运行记录要么都在要么都不在** —— 排障时两者必然对得上。
代价：事件查询与运行记录强耦合在同一库，将来拆库时事件要跟着走（可接受）。

### 决策 2：血缘查询「登录即可查」，只暴露名字与结构

权限模型里"数据"走授权，"元数据结构"不设门槛 —— 理由：

1. 血缘的价值恰恰是**跨人协作**：我要知道我改的东西会影响谁，而受影响的人未必是我可见的；
   如果血缘按权限裁剪，影响分析会静默漏掉看不见的下游 —— 那比看不到更危险；
2. 响应里**只有名字与层级**（无列、无行数、无数据），泄露面是组织结构本身，
   与"流程列表对非 owner 隐藏"不冲突（那边暴露的是配置与 SQL，这边只有名字）。

**代价（已知且接受）**：无授权用户能看到数据集名字的存在。
如果未来有"数据集名本身敏感"的需求，再对名字做脱敏（`已授权：N 个下游`），
接口形状不变。

### 决策 3：追溯用「当前版本」的 input_datasets，BFS 分层

- 每条流程取**最新版本**的 `input_datasets`（历史版本的血缘是审计，不是现状）；
- BFS 分层返回（层 0 = 自己，层 1 = 直接上下游…），上限 `depth`（默认 3，最大 6）；
- **防环**：访问过的数据集名不再展开；**防重复**：同一层内去重。

**为什么不用递归 CTE 在库里做**：数据规模是"流程数 × 平均输入数"的量级（几十到几百条边），
Python 内存 BFS 一次查几行就完，上递归 SQL 是把简单问题复杂化。

### 决策 4：事件 job 命名 `flow:<流程名>`，产物与输入用数据集名

OpenLineage 的 job/ dataset 命名空间都用 `bisql`。数据集名是平台的通用标识
（问数、授权、MCP 都用它），血缘沿用同一个词表 —— 跨功能对得上，不用翻译。

## Risks / Trade-offs

- **每次成功运行多一条 INSERT**。量级 = 编排运行频率，可忽略。
- **历史版本不参与血缘**（决策 3）：回滚到旧版并重跑后，血缘自然回到旧版的输入 ——
  语义正确（血缘跟"现在是什么"走，不跟"曾经是什么"走）。
- **前端分层列表在网状血缘下会重复展示同一节点**（一个数据集同时出现在两层）。
  应对：BFS 已保证每个节点只在其**首次发现**的层出现一次，列表不重复；
  真出现"想要图"的需求再上 React Flow 只读画布。
